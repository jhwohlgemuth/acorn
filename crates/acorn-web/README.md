# ACORN Research Intelligence

ACORN Research Intelligence is a local Dioxus application for nine ACORN operations, loaded Research Activities, and organization locations. RAD means Research Activity Data. The application inherits the workspace version and links `acorn-wasm` into the UI's single WASM payload. Its dependency graph excludes `acorn-lib` and `acorn-host`. Desktop/Tauri delivery remains planned.

## Develop and validate

```sh
make web-doctor      # Read-only prerequisite and development-port diagnostics
make web-setup       # Optional explicit setup: pinned Dioxus CLI and WASM target
make web-dev         # Dioxus :8080 and Vite map Fast Refresh :8083
make web-check       # Package formatting, native/WASM checks and strict Clippy
make web-test        # Packaging, native projections, real WASM, effects and assets
make web-build       # Static release and single-WASM/export verification
make web-preview     # Serve release assets on loopback :8080
npm --prefix crates/acorn-web/geospatial test
node crates/acorn-web/scripts/parity-smoke.mjs
```

Prerequisites: rustup-managed Rust/Cargo, Python 3, Node.js 22.17+ and `wasm-pack` (tested with 0.15.0). `.nvmrc` pins the same Node.js 22.23.5 release used by GitLab; run `nvm install` and `nvm use` from the repository root when needed. `make web-doctor` checks the web-development subset, the repository-managed Dioxus CLI and development ports without changing the machine; `wasm-pack` is additionally required by `web-test`. Browser Rust commands use the active rustup toolchain, including when Homebrew Rust appears first on `PATH`. GitLab installs checksum-verified Node.js 22.23.5 for `build-web`. `web-test` installs the map test dependencies before running them. `web-map`, included in dev/release builds, runs `npm ci --ignore-scripts` against the pinned map lockfile. Install browser-test dependencies with `npm ci --prefix crates/acorn-web` and `crates/acorn-web/node_modules/.bin/playwright install chromium` once. The parity script accepts an optional public-directory path, screenshot-output directory and base prefix; defaults are `target/dx/acorn-web/release/web/public` and `target/abw-parity`.

`WEB_PORT=8084` changes the Dioxus or preview port; Vite uses loopback port 8083. The coordinator passes the selected frontend origin to Vite; CORS permits only that port on `127.0.0.1` and `localhost`. Both names work when opening the development frontend. For standalone `npm run dev` with a custom frontend port, set `ACORN_WEB_DEV_ORIGIN=http://127.0.0.1:<port>`. `web-dev` and `web-build` automatically run `web-setup` if the local Dioxus executable is missing (including after cleaning `target`). The first run may take longer while Cargo installs the pinned CLI. `DIOXUS=/path/to/dx` overrides `target/tools/dioxus/bin/dx`; custom executables are checked and never replaced automatically. The development coordinator uses plain Dioxus logging, waits for Vite readiness, stops both process groups on exit and restores terminal settings on POSIX hosts; Windows uses native process groups. A port conflict fails without terminating another server. Compatible map TSX/CSS edits use Vite Fast Refresh/HMR; `main.tsx`, dependency/config changes and Rust changes can require a reload/rebuild. The map config names `src/main.tsx` as the dependency-scan entry and warms it, so Vite pre-bundles Cesium, React and Resium at startup instead of reloading mid-load on a cold cache. Map initialization failures are logged as strings so `dx` can display them. `node crates/acorn-web/scripts/dev-smoke.mjs http://127.0.0.1:8084` checks map refresh with temporary source edits restored in `finally`; run it only with no concurrent map editor. Dioxus owns the surrounding RSX/CSS/static watcher. Production embeds local static assets without either development client.

Cargo stages canonical artwork, the unchanged WebMCP adapter and the verified skill bundle before asset macros expand. Generated staging is ignored. Use `make web-map web-prepare` before a direct `dx` build; ordinary Cargo checks do not build the JavaScript map or editor. Both use directory assets, so native workspace lint, test and coverage jobs can compile from a clean checkout without Node or generated JavaScript bundles. Browser builds still require those bundles. Release builds use the `web-release` profile and `--debug-symbols false` to avoid the Dioxus 0.7.3/Binaryen DWARF failure. The package check rejects a second WASM payload, missing operation exports or retained DWARF sections. The crate has `publish = false`; its distribution is the website.

## Local workspace and tools

Home pairs the ACORN banner with a **Research Intelligence** subtitle and the tagline **Plant an acorn, grow your science**. Adjacent tour and **Try Sample Data** actions, Skill entry, paired file/folder and drop loaders, and expandable remote loading complete the page. The empty layout fits desktop, portrait and landscape viewports; expanded content can scroll. The sidebar starts with its directional collapse/expand control and compact navigation, without an icon header. Its collapsed state survives navigation and reloads within the current browser tab. A compact Portfolio shortcut always shows activity and file counts, including `0 activities · 0 files` for an empty session. Its tooltip clarifies validation and the selected file; the collapsed sidebar keeps both counts. The RAD footnote and fixed bottom credit appear only on Home. The browser tab uses the canonical brown ACORN SVG favicon. The sample action explicitly loads and validates a fictional 20-file bucket with four validated JSON RAD records, then opens Portfolio. **Use example** sits in each Input header, shares the Home sample-action styling, and only fills its editor. ACRE 2.0.0 is a separate CLI configuration download, not a browser validation tool.

Loaded files are saved automatically in localStorage and restored after reload until **Delete all data** in Settings. The loader accepts `.json`, `.yaml`, `.yml`, `.md`, `.txt`, `.svg`, `.png`, `.jpg`, `.jpeg`, and `.webp`, with 500 files, 20 path segments, 2 MiB per file and 32 MiB stored total. Raster bytes must match the extension's PNG, JPEG, or WebP signature and are stored as canonical data URLs; encoded bytes count toward the total. Text files require UTF-8. The loader rejects unsafe paths and unsupported files, sorts relative paths, reports skipped entries and preserves the prior session on cancellation or total failure. Folder selection is capability-detected; unsupported browsers retain single-file loading. The expandable tree selects text without running a tool; image entries open a preview without entering the text editor. Portfolio validates loaded JSON only when requested. Its Research Activity Index derives projects from RAD `meta.identifier` and activities from validated source paths; invalid and unvalidated files stay in the file tree but never enter the index. Search covers titles, descriptions, section text, people, organizations, identifiers and paths. Result counts, alphabetical/relevance sorting, compact project lists and cards, activity details, related activities, pinned source links, and deduplicated metrics update when the workspace changes or is restored. Project cards show one associated image at a time; touch swipes and overlaid arrow controls move between SVG and raster images, with a placeholder for any missing reference. Matching activities stay in the sortable table below the projects in both List and Cards views, and their detail overviews include associated images. Replacing the workspace or deleting all app data removes stale validation and index rows.

Public GitHub and GitLab repositories, folders and file web URLs can be loaded from Home. GitHub also accepts `owner/repo`; GitLab supports nested groups and public self-hosted instances with CORS enabled. An optional branch, tag or commit is resolved to an immutable commit before downloading. Enter slash-containing branch names explicitly. Anonymous requests omit credentials; authenticated repository requests use bearer authorization and accept same-origin redirects. Supported image files use the same signature and encoded-size checks as local files. Loads are cancellable, limited to 10,000 listing entries and the same file/session limits, retry failed GitLab raw downloads by blob ID, request LFS content from GitLab, skip oversized, invalid or unavailable files with a reported count, and replace the session only after success. API limits and servers without browser CORS support show an error while preserving the session. GitLab tree pagination follows the server-provided next cursor. GitHub currently requires the repository recursive listing to fit the listing limit, even for a folder or file URL. Both remote input fields offer native autocomplete from the 20 most recent unique submitted values in local storage. Valid repository inputs are remembered even when a download fails or is cancelled; rejected URLs and blank revisions are omitted. **Clear suggestions** removes this history. Unavailable or full browser storage does not block loading.

Every tool offers a compact **Load content** control. Open it to **Choose file** or **From URL → Load URL**; connection details stay in **Link tips**. The tray closes after a successful load and returns focus to the editor. Close it with **×** or Escape to cancel a pending download and return to the launcher. On Home, choose **Open file or folder → URL** to load a single file into the workspace. Direct HTTPS URLs (including query parameters) and GitHub/GitLab file links are supported; repository web links are converted to raw-file URLs. Downloads omit credentials and referrers, follow browser-approved redirects, enforce the destination tool’s UTF-8 byte limit while streaming, and time out after 30 seconds. Cancel, failed downloads, oversized responses and invalid UTF-8 preserve the existing content. Navigating away or selecting a local file cancels pending downloads. Servers must permit cross-origin browser access (CORS); otherwise download the file locally and choose it from disk. URL inputs are not saved to browser history by the app. Loading supplies content without automatically running validation or analysis.

Repository loads may use one explicitly entered token for the current tab in a secure browser context. Add or replace it beside Home’s repository loader; Settings shows the masked token status and a forget action. The token is sent to the HTTPS host of each repository URL selected in the tab, and is held in `sessionStorage` across reloads, separate from the saved workspace. An older project-bound tab token remains limited to its original repository until it is saved again as an app token. Choose a short expiration and limit [GitHub fine-grained tokens](https://docs.github.com/en/rest/repos/contents) to the repositories they need with Contents read. For the current GitLab project, commit and tree API discovery path, a legacy personal access token or project access token can use [GitLab's documented `read_api` scope](https://docs.gitlab.com/security/tokens/access_token_scopes/); prefer a project token when available to limit its reach. GitLab documents `read_repository` for Git-over-HTTP and repository-file access, while `read_api` grants read access to the API; the browser's project/commit/tree discovery path uses `read_api`. On November 16, the user loaded the private NSSD project at `https://www.jasonwohlgemuth.com/acorn/` using the token flow after the app displayed the `read_api` requirement. Chromium showed 38 files loaded, 40 entries skipped, zero validated activities, and a masked token configured for `code.ornl.gov`. The successful cross-origin request verifies browser CORS for this origin and project. The browser UI does not expose the raw token scope or commit ID; source and test coverage verifies revision pinning, bearer authorization, same-origin redirects, redaction, token removal, and separation from workspace/history storage. The selected provider API receives the token in a request header, with redirects to another host rejected. Public loads work without a token. A token is never added to URLs, suggestions or saved workspace data; errors are redacted. The browser cannot protect a session-storage token from scripts running on its origin, so use only a trusted deployment and revoke a token at its provider if needed. Long-term token persistence is a no-go for this browser release; closing the tab session, **Remove token**, or Settings’ **Forget repository token** clears it. GitHub.com and HTTPS GitLab hosts selected by the user are supported; browser CORS policy must allow the request.

## Application publishing lifecycle

`acorn-web` and `acorn-desktop` are application distributions. `packaging/applications.json` records both independently of the crates.io release list. Rust release commands live in `xtask/src/application_release/`. `make check-release-apps` runs `cargo xtask check-release-apps`, checks coverage, workspace version inheritance, `publish = false` and pending desktop work, and runs the Rust packaging/upload regression tests.

`make release-version VERSION=X.Y.Z` runs that application check before changing the workspace version, then updates dependency pins, `CITATION.cff` and `Cargo.lock` and verifies crate/version consistency. The browser package, UI version, archive name and embedded release metadata derive from the workspace version. After the version change reaches GitLab main, CI builds and publishes the matching browser ZIP and checksum. The command itself does not build or upload artifacts. Desktop remains an explicitly planned distribution until its native crate and packaging jobs exist; it has no artifact to release yet.

`make web-package` builds the browser, verifies the single WASM payload and nine operation exports, then writes `bin/acorn-web-v<VERSION>.zip` and its `.sha256` sidecar. Extract the ZIP and serve it over HTTP at the origin root. `release.json` inside the archive records the source revision, workspace version, file hashes and application publication states. Archive bytes are reproducible for identical inputs.

On merge requests and relevant default-branch changes, `build-web` checks, tests and packages the browser. On the existing default-branch `Cargo.toml` release trigger, it also runs `make web-publish`, using `CI_JOB_TOKEN` and `PKG_REGISTRY_URL`. Publication verifies the existing archive before uploading it to `acorn-web/v<VERSION>/` in the GitLab generic package registry. The release job waits for this build/upload and exposes ZIP and checksum links labeled **browser preview**. Existing identical remote bytes are accepted on retries; different bytes at the same URL are rejected. `make web-package` delegates to `cargo xtask package-web`; `make web-publish` delegates to `cargo xtask publish-web`. The latter performs a real upload and does not rebuild. GitHub Pages deployment is handled separately by the mirror workflow below.

The browser remains a preview while its documented acceptance and optimizer limits remain open. These registry URLs use the project's access policy; anonymous public access has not been established. The desktop crate does not yet exist. Its inventory entry remains `planned`, and no native download is advertised. ABW-11 must add the crate with workspace version inheritance and `publish = false`, move the inventory to `development`, and add native build checks and the Cargo packaging exclusion. ABW-23–30 must add signed native artifacts, release links and package-manager publication using the same immutable upload path, with actual public-download/signing evidence. Desktop packaging must retain the shared frontend version and digest and use identifiers distinct from the CLI.

For an existing browser build, run `cargo xtask package-web` and `cargo xtask verify-web` without rebuilding. Both accept `--output DIR`; packaging also accepts `--source DIR`. The CLI artifact uploader uses the same `cargo xtask upload-artifact FILE HTTPS_URL` implementation. Release checks, packaging, verification and HTTP uploads require no Python runtime.

## GitHub Pages mirror deployment

GitLab remains the source repository. Its enabled push mirror updates protected branches in `jhwohlgemuth/acorn`. `.github/workflows/acorn-web-pages.yml` deploys the browser preview after each mirrored push to `main`; it also supports a manual run on `main`. Other branches and forks cannot deploy through this workflow. Pages is a continuously updated preview of mirrored main, independent of the versioned GitLab ZIP releases.

The build reads the Pages `base_path`, runs `make check-release-apps`, builds with `make web-pages`, and runs `make web-test-pages` in Chromium before uploading only the generated public directory. The deploy job uses GitHub's Pages artifact and OIDC actions with `pages: write` and `id-token: write`; no GitLab token, personal deployment token, generated branch or additional backend is needed. Deployments are serialized so an active deployment is not interrupted by a later mirror push.

`web-pages` adds an identical `404.html` and a `.nojekyll` marker. A direct tool URL or refresh receives GitHub Pages' HTTP 404 response, then boots the application at that route. This preserves the URL and navigation; it does not change the server response to HTTP 200. The smoke test checks this behavior, stylesheet and image loading, local WASM execution, router links, and failed or unexpected network requests.

Reproduce the project-site build and browser check locally:

```sh
npm ci --prefix crates/acorn-web
# One-time browser installation; Linux CI also passes --with-deps.
crates/acorn-web/node_modules/.bin/playwright install --only-shell chromium
make web-pages WEB_BASE_PATH=/acorn
make web-test-pages WEB_BASE_PATH=/acorn
```

`make web-build` adds a `<link rel="preload">` for the hashed WASM to `index.html` (`scripts/preload-wasm.mjs`), and `index.html` shows a loading shell until the application mounts. `make web-test-pages` also fails if Discover at the 16 KiB editor limit takes 3 s or longer; November 14, 2026 release builds measured 67–77 ms in Chromium. Remaining runtime work is tracked in the [browser performance plan](../../.wiki/refactors/browser-performance.md).

All nine operations, Home sample loading and Portfolio validation run in one module worker (`assets/worker.js`) so the interface keeps painting. The worker imports the same release loader and WASM as the page; `main` launches Dioxus only when a `document` exists, so the release still ships one payload. The worker calls the `runOperation` export, which applies the same request validation, operation dispatch and 256 KiB result limit as `operations::run`. `window.acornOperations` in `effects.js` starts the worker when a tool page opens and sends one operation at a time. If the worker or its WASM cannot load (no module-worker support, or the loader script is missing), the app turns the worker off for the session and runs operations on the main thread after painting the busy state. A WASM trap inside the worker reports a failed operation and the next request starts a fresh worker. The worker holds a second WASM instance, so memory use roughly doubles while it runs. WebMCP tools still call the page's bindings directly. `make web-test-pages` checks that operations were served by the worker and that no main-thread frame gap during a 16 KiB discovery reaches 250 ms.

The GitHub repository is configured with Actions enabled, Pages' publishing source set to **GitHub Actions**, and the `github-pages` environment restricted to `main`. GitHub assigns the project site to the account's existing domain at `www.jasonwohlgemuth.com/acorn/`; the hosted browser is live and was used for private GitLab acceptance on November 16, 2026. The site responds over HTTPS. Confirm the Pages HTTPS-enforcement setting separately before claiming that the setting is enabled. The GitLab mirror credential must be allowed to push workflow files (the `workflow` scope for a classic GitHub PAT). Keep workflow changes in GitLab so later mirroring does not overwrite GitHub-only edits. This setup does not change `acorn.ornl.gov` or publish desktop installers.

References: [GitHub custom Pages workflows](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages), [Dioxus base-path configuration](https://dioxuslabs.com/learn/0.7/guides/tools/configure/).

Local hosting evidence: release builds and Chromium 158 smoke tests passed for `/acorn/` and an empty root base path. Both loaded assets, ran Research Activity validation, navigated within the configured prefix, and refreshed a direct Readability route through the Pages-style 404 response. The optimizer fallback was subsequently removed by the verified debug-symbol repair; this local hosting evidence does not claim a live GitHub deployment or a full browser matrix.

## Interface conventions

The shared shell and information pages follow the [OKF Plan Browser](https://www.jasonwohlgemuth.com/okf-plan-browser/) layout: 220px navigation, a theme-aware ACORN Home banner, 420px welcome column, paired load tiles, a sample action to the right of the tour button, and rounded cards with consistent section spacing. The published Home, Settings and About components were compared on November 12, 2026; the reference's direct `/home` HTTP route returned 404, so the app root and its published page assets supplied the comparison. ACORN accepts both `/` and `/home`.

ACORN retains its canonical artwork and green primary action (`#00662c`). Dark surfaces follow the [OKF browser theme](https://www.jasonwohlgemuth.com/okf-plan-browser/assets/index-BgyxskE8.css): canvas `#1f2229`, cards/sidebar `#252931`, borders `#3c414e`, and hover/selection `#2e333d`. Muted One Dark text (`#abb2bf`) accompanies One Dark Pro syntax colors in read-only code and editable CodeMirror blocks, with readable light-theme variants. ORNL green text selections work for single words and multiple lines; translucent active-line shading preserves selection visibility. Secondary text uses a muted gray (`#969daa`) that retains 4.5:1 contrast on interactive surfaces. Text and focus tokens have contrast checks in both themes. Research-specific screens use icon-led titles, unnumbered input/result sections, explicit validation actions, numeric portfolio metrics, selected-row and sort-direction indicators, and actionable empty filter states. The sidebar scrolls independently so all tools remain reachable on short screens. Emoji supplement labels; icon-only controls retain accessible names.

The parity smoke test covers Home action order, deep linking, sidebar labels, filter reset, all nine operations, theme selection, local imports, skill downloads, mobile reflow, 200% zoom and the map fallback. Its screenshots are review artifacts; automated checks alone do not establish pixel equivalence or institutional brand approval.
